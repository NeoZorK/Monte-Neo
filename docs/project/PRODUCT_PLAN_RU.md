### Найдено и исправлено в v0.35.1 (PR #70)

1. **Сломанные бары проходили проверку данных.** Close на 20% выше high или open вдвое ниже low давали «OHLCV is clean». Теперь такие бары отклоняются (допуск 0,1% на округление поставщиков).

## 3. Конкуренты и наше место

| Инструмент | Что делает | Чего у него нет по сравнению с нами |
|---|---|---|
| QuantStats, pyfolio | Красивые отчёты (tear sheets) по доходностям | Не ищут утечки, не проверяют код, не учитывают перебор вариантов, нет сертификатов |
| vectorbt, backtrader, zipline, bt | Фреймворки бэктеста | Исполняют любой код; сами не говорят, что бэктест сломан |
| freqtrade `lookahead-analysis` | Ищет утечки в стратегиях freqtrade | Только freqtrade, только крипто, нет статистики отбора и сертификатов |
| mlfinlab, skfolio, arch | DSR, PBO, SPA-тесты как библиотечные функции | Нужно самому собрать конвейер; нет проверки кода, отчёта, агентов |
| QuantConnect Lean | Облачная платформа | Закрытая экосистема, проверка методологии не является продуктом |

**Наше уникальное место:** независимый верификатор, который (1) исполняет чужой код и доказывает утечки, (2) учитывает издержки и перебор, (3) выдаёт подписанный воспроизводимый сертификат, (4) встроен в ИИ-агентов через MCP.

**Как стать полезнее большинства квант-фреймворков: не конкурировать с ними, а стать слоем проверки поверх любого из них.** Нужны адаптеры: результат vectorbt / backtrader / freqtrade / Lean → проверка Monte-Neo.

## 4. Отчёт: стоит ли делать красивее? Да

Отчёт — лицо продукта для людей, которые принимают решения по деньгам: аллокаторов, проп-фирм, преподавателей. Сейчас он аккуратный, но это страница с таблицами, а не профессиональный tear sheet уровня QuantStats. Что сделать:

1. **Шапка-вердикт с объяснением одним предложением.** Например: «Отклонено: стратегия видит следующий бар (строка 6), а после издержек теряет 65%».
2. **Карточки по категориям:** данные / утечки / экономика / статистика с числом pass/warn/fail и цветом.
3. **Графики:**
   - капитал в логарифмической шкале против «купи и держи»;
   - просадка («подводный» график);
   - скользящий Sharpe;
   - **тепловая карта доходности по месяцам** (стандарт индустрии);
   - гистограмма распределения доходностей;
   - **гистограмма теста значимости**: доходности 200 сдвинутых копий и реальная — очень наглядно;
   - **кривая чувствительности к издержкам:** доходность при 0…50 б.п.;
   - для grid — **тепловая карта параметров** (плато или пик видно сразу).
4. **Статистика сделок:** доля прибыльных, profit factor, средняя прибыль и убыток, среднее время удержания, лучшая и худшая сделка, серии.
5. **Доказательства утечки:** на каком баре и в какой точке проверки изменился сигнал, строки кода из линтера с подсветкой.
6. **Экспозиция во времени,** для набора инструментов — топ-символы по вкладу в результат.
7. **Печать в PDF** (CSS `@media print`), логотип, аккуратная типографика, иконки статусов.
8. **Галерея примеров** на сайте документации: 3–4 реальных отчёта («утечка», «нет преимущества», «честная стратегия»).

Технически: остаёмся в чистом SVG без JS и внешних ресурсов — это преимущество для приватности и офлайна. Чтобы строить графики сделок и тепловые карты, в сертификат добавляется компактный блок `trades` и месячные доходности (до ~20 КБ).

## 5. Профессиональная статистика: чего не хватает

| Функция | Зачем | Приоритет |
|---|---|---|
| **Качество данных (R3):** выбросы (robust z по лог-доходностям с возвратом), застывшие цены, пропуски во времени, сплиты, нулевой объём, выходные у 24/7-данных | Главный источник фальшивой прибыли после утечек | P0 |
| **Сверка заявленного (R8):** `--claim claim.json` → проверка «overclaim» | Прямой ответ на «агент соврал про Sharpe» | P1 |
| **PBO (CSCV)** — вероятность переобучения при переборе параметров | Стандарт López de Prado; идеально ложится на `verify_grid` | P1 |
| **Доверительные интервалы** Sharpe и доходности (блочный бутстрэп) | Профессионалы спрашивают «насколько уверены» | P1 |
| **Minimum Track Record Length** | «Сколько данных нужно, чтобы поверить этому Sharpe» | P2 |
| **Реалистичные издержки:** спред из high-low (Corwin–Schultz / Abdi–Ranaldo), доля от среднего объёма (ёмкость стратегии), плата за шорт и фандинг, издержки по символам в наборе | Самый частый вопрос трейдеров: «а на реальном объёме?» | P1 |
| **Ёмкость стратегии (capacity):** при каком капитале преимущество исчезает | Для фондов и проп-фирм | P2 |
| **SPA / White Reality Check** для перебора | Академическая строгость для исследователей | P3 |
| **SL/TP внутри бара (R9)** в движке весов | Реалистичность стратегий агентов | P2 |
| **Walk-forward для одиночной стратегии** (скользящие окна), стабильность по годам | Уже частично есть; нужна отдельная проверка | P2 |

## 6. Расширение Trap Suite: цель — 80 ловушек и 35 честных контролей

Сейчас 54 ловушки и 25 контролей. Новые ловушки по группам:

**Машинное обучение (частая ошибка агентов):**
1. `train_test_split(shuffle=True)` на временном ряду, метка — будущая доходность.
2. `KFold(shuffle=True)` / кросс-валидация без зазора (purging/embargo).
3. `StandardScaler().fit` на всём ряду, затем скользящее окно (есть частично).
4. Отбор признаков по корреляции с будущей доходностью на всей выборке.
5. Подбор гиперпараметров на всей выборке и тест на ней же.

**Время и календарь:**
6. Дневной индикатор слит с внутридневными барами без сдвига (дневной close известен утром).
7. `resample(label="left", closed="right")` — неверная метка корзины.
8. Сдвиг часового пояса: «дневной» бар закрывается раньше биржи.
9. `pd.merge` по дате без `shift(1)` для данных «на конец дня».
10. Скрытый сдвиг через срез: `np.append(c[1:], nan)` (линтер не видит, пробы ловят).
11. Цикл `sig[i] = c[i+1] > c[i]`.

**Данные:**
12. Выброс цены ×10 на одном баре, на котором «зарабатывает» стратегия (нужна проверка R3).
13. Застывшая цена (данные не обновлялись) → «идеальный» mean-reversion.
14. Несплит-корректированные цены (скачок −50%).
15. Делистинг с нулевой доходностью вместо −100% (набор инструментов).

**Наборы инструментов:**
16. Отбор символов по итоговой доходности за весь период.
17. Сегодняшний состав индекса применён к прошлому.
18. Ранг по будущей волатильности.
19. Нормировка весов по сумме за весь период.

**Размер позиции:**
20. Размер позиции по будущей волатильности всего ряда.
21. Плечо, подобранное по итоговой просадке.

**Отбор и перебор:**
22. Выбор лучшей даты начала теста.
23. Выбор лучшего инструмента из многих без учёта `n_trials`.

**Честные контроли для новых групп:** walk-forward ML с зазором, `TimeSeriesSplit`, дневной индикатор со сдвигом, корректное слияние по времени, точка-во-времени состав индекса и другие.

Бонус для маркетинга: рубрика «ловушка недели» в соцсетях — каждая ловушка — готовый пост с кодом.

### Этап 1в — ✅ вариант А по numba выполнен (29.09.2026, в v0.36.2 / следующем выпуске)

## 12. Детальная проверка безопасности (security check)

Продукт по своей природе исполняет чужой код и выдаёт документы, которым доверяют деньги. Поэтому нужна отдельная систематическая проверка:

| Область | Что проверить и сделать |
|---|---|
| Модель угроз | Описать активы (ключи подписи, сертификаты, машина пользователя), нарушителей (автор стратегии, подделыватель сертификата, злоумышленник в сети) и границы доверия; опубликовать в SECURITY.md |
| Исполнение чужого кода | Песочница `--isolate` (раздел 2, R2): отдельный процесс, запрет сети и записи файлов через audit-hook, лимиты памяти и времени; тесты на попытки выхода из песочницы |
| MCP-сервер | Режим HTTP должен слушать только `127.0.0.1` по умолчанию, с явным предупреждением при другом адресе; `render_report` и другие инструменты не должны писать за пределы рабочей папки; лимиты размера входных файлов |
| Подписи | Ревизия канонизации JSON и Ed25519 (атаки подмены полей, дублирующиеся ключи, NaN/Infinity, Unicode-нормализация), права файлов ключей, ротация ключей; фаззинг парсера сертификатов в Python и в JavaScript страницы проверки |
| HTML-отчёт и страница проверки | Тесты XSS на всех полях (частично есть), Content-Security-Policy в отчёте, проверка `?cert=` на странице (откуда грузится, какие схемы URL разрешены) |
| Цепочка поставки | Закрепить все GitHub Actions по SHA коммита вместо тегов (сейчас `@v4`, `@v7`), Dependabot для Actions и pip, `pip-audit` в CI, SBOM (CycloneDX) к каждому выпуску, аттестации сборок (Sigstore / GitHub attestations), OpenSSF Scorecard; публикация в PyPI уже через доверенную публикацию без токенов — сохранить |
| Статический анализ | Bandit и Semgrep в CI (CodeQL уже работает); разобрать все находки |
| Секреты | Сканирование истории на секреты, правила для ключа подписи в Action (уже: временный файл с правами 600 и удаление) |
| Отказ в обслуживании | Огромные файлы, миллионы символов, бесконечные стратегии — лимиты и понятные ошибки |
| Процесс | Выпуски с исправлениями безопасности — в любое время; раздел «Supported versions» и сроки ответа в SECURITY.md |

Результат: отчёт аудита безопасности в репозитории, исправления, тесты и бейдж OpenSSF Scorecard.

## 13. Скорость: максимальна ли она и поможет ли Apple Metal в 100–1000 раз?

**Замер (v0.35.1, один инструмент, 200 000 баров, проверка 5,2 с):**

| Часть | Время | Доля |
|---|---|---|
| Сама стратегия пользователя (56 вызовов для проб) | 0,44 с | ~9% |
| Движок бэктеста (numba), издержки, задержки, сдвиги | < 0,1 с | < 2% |
| **Наши накладные расходы:** повторный разбор меток времени (4 раза), разбивка по периодам циклом Python по 200 тыс. дат (1,4 с), копирование таблицы перед каждым вызовом стратегии, преобразования | ~3 с | **~60%** |
| Прочее (загрузка, линтер, отчёт) | остальное | |

На наборе 300 символов × 1500 дней (7,4 с) больше половины времени — вызовы стратегии пользователя (pandas `groupby`) внутри проб.

**Вывод: скорость не максимальная, но главный резерв — не в GPU.**

1. **Убрать накладные расходы** (этап 1): разбирать метки времени один раз, векторизовать периоды через `datetime64`, не копировать данные лишний раз. Ожидаемо **в 2–3 раза** быстрее для больших рядов.
2. **Параллельные пробы на ядрах CPU** (`--jobs`): 56 вызовов стратегии независимы. На Apple M-серии с 8–12 ядрами это **ещё в 4–8 раз** для тяжёлых стратегий.
3. **Кэширование:** повторная проверка тех же данных и кода (например, при `--recheck` или в CI) может брать результат проб из кэша.

**Apple Metal в 100–1000 раз — честный ответ: для проверки в целом невозможно.**
- Основное время — Python-код стратегии пользователя (pandas). GPU не умеет исполнять произвольный Python, а переносить стратегии на шейдеры — значит заставить пользователя переписать код.
- Движок бэктеста уже занимает меньше 2% времени. Ускорив его даже в 1000 раз, общая проверка станет быстрее лишь на ~2% (закон Амдала).
- Metal есть только на Mac: пользователи Linux, CI и облачные агенты ничего не получат.

**Где Metal (через MLX, который уже есть в проекте) действительно даст 10–100 раз:** в будущих тяжёлых расчётах Монте-Карло, где тысячи бэктестов идут на одних и тех же позициях:
- бутстрэп доверительных интервалов (10 000 выборок);
- PBO/CSCV (тысячи комбинаций разбиений);
- тест сдвигов с 10 000 копий вместо 200;
- сетки параметров до тысяч комбинаций на наборах инструментов.

Для них предлагается пакетный движок: numba `prange` на CPU (работает везде) и MLX/Metal на Mac как ускоритель. Критерий включения — выигрыш не меньше 5× на реальных размерах и совпадение результатов с CPU до 1e-9.

**Цели по скорости (добавлены в этап 1):**
- 200 тыс. баров, простая стратегия — ≤ 2 с (сейчас 5,2 с);
- набор 300 × 1500 — ≤ 3 с при `--jobs 8` (сейчас 7,4 с);
- холодный старт MCP через `uvx` — ≤ 5 с (сейчас до 18 с).

## 16. Уйти от numba на Apple Metal или сделать numba необязательной? (исследование 29.09.2026)

**Замеры (Linux, 4 ядра; движок знаков, 200 000 баров):**

| Вариант | Один бэктест | Совпадение с сертификатами |
|---|---|---|
| numba (сейчас) | 1,2 мс | эталон |
| тот же код на чистом Python (без numba) | 190 мс (в 160 раз медленнее) | до бита |
| Metal (GPU Apple) | не измерялось — см. ниже | **невозможно** |

**Доля движка во времени проверки после исправлений v0.36.1:** 2–7% для обычных стратегий, до 38% для стратегий со сделкой на каждом баре (было 90% из-за журнала сделок в Python — исправлено, в 19 раз быстрее).

**Metal — нет, по трём причинам:**
1. **Нет двойной точности.** Шейдеры Metal (MSL) не поддерживают `double`; MLX считает `float64` только на CPU. Движок во float32 даст другие числа → другой ID сертификата на Mac и на Linux, то есть сломает главное обещание: «сертификат воспроизводится где угодно».
2. **Только Mac.** GitHub Action, CI, облачные агенты и MCP на Linux ничего не получат, а код движка придётся поддерживать дважды.
3. **Нечего ускорять.** Движок — 2–7% времени; остальное — стратегия пользователя (pandas) и наш Python. Даже бесконечно быстрый GPU ускорит проверку максимум на эти проценты. Плюс затраты на передачу данных на GPU для одного бэктеста больше, чем сам бэктест на CPU (1 мс).

Metal/MLX остаётся кандидатом только для будущих пакетных расчётов (тысячи бэктестов: бутстрэп, PBO/CSCV, 10 000 сдвигов) — и только как ускоритель с проверкой совпадения, не как источник чисел для сертификата.

**Сделать numba необязательной — можно, и это безопасно для сертификатов.** Исходный код ядра на чистом Python даёт те же числа до бита (проверено: `py_func` против скомпилированной версии). Что это даст и чего стоит:

| | С numba (сейчас) | Без numba |
|---|---|---|
| Размер установки | 327 МБ | ~135 МБ (llvmlite 175 МБ + numba 17 МБ уходят) |
| Холодный старт | +4 с компиляции один раз | нет компиляции |
| Проверка 3 000 баров | ~0,03 с | ~0,1 с (незаметно) |
| Проверка 100 000 баров (прибыльная стратегия, идёт тест сдвигов) | ~1 с | ~46 с (знаки), ~170 с (веса) |
| Убыточная стратегия, 200 000 баров | ~0,3 с | ~1,5–4,5 с |
| Поиск по сетке | секунды | минуты–часы |
| Платформы | где есть колёса numba | везде, где есть numpy (новые Python в первый день, Alpine, Pyodide/браузер) |

**«Сама докачается, если нужно» — не рекомендую.** Установка пакетов во время проверки:
- ломает режим без сети (`--isolate`, Docker `--network none`, закрытые CI) — именно там, где верификатор нужнее всего;
- это атака на цепочку поставки: инструмент доверия не должен сам скачивать и исполнять код;
- делает результат зависимым от того, что лежало на PyPI в момент запуска.

**Решение владельца (29.09.2026): вариант А.**
- Вариант А (выбран): numba остаётся в базовой установке там, где для неё есть готовые колёса (условие платформы в зависимостях), а код работает и без неё — запасной путь на чистом Python с теми же числами. На новом Python в первый день, Alpine, в браузере установка больше не падает: проверка работает медленнее и подсказывает `pip install "monte-neo[fast]"`, когда numba станет доступна. Размер для обычных пользователей не меняется. Ничего не скачивается само.
- Вариант Б: базовая установка без numba (~135 МБ), numba — в extra `fast`; Action, Docker-образ и интеграции для агентов ставят `fast` сами. Лёгкая установка для большинства, но на больших данных «из коробки» в 10 раз медленнее.
- В обоих вариантах: при больших данных без numba — подсказка в выводе, никакой автозагрузки.
