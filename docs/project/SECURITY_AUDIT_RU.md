# Аудит безопасности Monte-Neo (этап 1б)

Дата: 29.09.2026. Версия на момент аудита: v0.36.1. Исправления — в v0.37.0.
Внешняя политика и модель угроз для пользователей: [SECURITY.md](../../SECURITY.md) (на английском).

## Что проверено

| Область | Как проверено |
|---|---|
| Исполнение чужого кода (`--isolate`) | Попытки выхода: запись вне временной папки, переименование, символические и жёсткие ссылки |
| Сертификаты и подписи | Разбор кода `signing.py`, `recheck.py`; мутационный фаззинг (600 изменённых сертификатов), мусор в блоке подписи (более 3000 комбинаций), случайные байты вместо файла |
| Страница проверки в браузере | Разбор `verify-certificate.js`: парсер, вывод, загрузка по `?cert=`; сравнение с Python |
| HTML-отчёт | Фаззинг: во все строки сертификата подставлялись вредоносные значения; проверка отсутствия скриптов |
| MCP-сервер | Разбор инструментов, привязка HTTP-режима, запись файлов |
| Входные данные | Размеры файлов, глубина JSON, `NaN`, дубли ключей, `.npy` с pickle |
| Зависимости | `pip-audit` по заблокированным зависимостям (основные и все extras) |
| Статический анализ | Bandit по коду верификатора; CodeQL уже включён |
| Цепочка поставки | Все GitHub Actions, права workflow, публикация релиза |
| Секреты | Поиск ключей и токенов по всей истории git (226 коммитов) |

## Найдено и исправлено

| № | Серьёзность | Находка | Исправление |
|---|---|---|---|
| 1 | **Высокая** | `--isolate` обходился: временный файл можно переименовать (`os.rename`, `os.replace`) поверх любого файла — проверялся только источник; ссылка (`os.symlink`, `os.link`) во временной папке позволяла затем писать в любой файл. Воспроизведено на четырёх сценариях | Проверяются оба конца переименования, ссылки запрещены, пути разворачиваются через `realpath`. Четыре теста падали до исправления и проходят после |
| 2 | Средняя | Открытый ключ внутри сертификата трактовался как имя файла: сертификат с `"public_key": "/путь"` заставлял верификатор открывать произвольный файл; несуществующий путь ронял проверку исключением | Ключ из сертификата — только текст (`allow_file=False`); файл допустим лишь для ключа, который указал сам пользователь |
| 3 | Средняя | Страница проверки показывала зелёную галочку «Valid signature (integrity only)» для сертификата, подписанного собственным ключом злоумышленника, если в ссылке не было `key=` | Зелёная отметка только при совпадении с ожидаемым ключом; без него — предупреждение «подпись цела, подписавший не проверен»; пояснения в результате |
| 4 | Низкая | JSON сертификата принимался нестрого: дубли ключей, `NaN`, вложенность до предела рекурсии; парсер страницы принимал битые `\u`-последовательности и управляющие символы | Строгий разбор в Python и в JavaScript с одинаковыми правилами (без дублей, без `NaN`, глубина ≤ 100) |
| 5 | Низкая | MCP-инструмент `render_report` мог записать HTML-содержимое в любой путь (риск при внедрении инструкций в агента) | Разрешены только `.html` / `.htm` |
| 6 | Низкая | Нет ограничений на размер входных файлов | Лимиты: таблицы 2 ГБ (`MONTE_NEO_MAX_INPUT_MB`), сертификат 64 МБ, файл стратегии 5 МБ, сетка 1 МБ, ключ 4 КБ; понятные ошибки |
| 7 | Низкая | Страница загружала `?cert=` без таймаута и лимита размера | Таймаут 15 с, лимит 8 МБ, без учётных данных и заголовка Referer |
| 8 | Низкая | HTML-отчёт без Content-Security-Policy, ссылка без `noopener` | Политика `default-src 'none'`, запрет форм и `base`, `noopener noreferrer`, `referrer: no-referrer` |
| 9 | Низкая | Уязвимость в зависимости `click` 8.3.1 (через `mcp` → `uvicorn`) | Обновлён в `uv.lock` до 8.5.0; `pip-audit` — без находок |
| 10 | Информационная | Bandit: 11 находок уровня Low — ложные срабатывания на словарях с ключами «PASS» / «good» (принимаются за пароли) и один `assert` | `assert` заменён явной проверкой; в CI Bandit падает от находок Medium и выше |

## Цепочка поставки: что сделано

- Все 24 использования GitHub Actions закреплены по SHA коммита (с комментарием-тегом, чтобы Dependabot их обновлял); тест не даёт добавить незакреплённое.
- Все workflow начинают с прав «только чтение»; запись (Pages, релиз) — на уровне задач (`docs.yml`, `release.yml`); тест это проверяет.
- Новый `security.yml`: Bandit и `pip-audit` при каждом push в main, в PR и раз в неделю.
- Новый `scorecard.yml`: OpenSSF Scorecard раз в неделю (результаты — в code scanning).
- К каждому релизу прикрепляется SBOM (CycloneDX) опубликованного пакета (шаг «не критичный»: его сбой не отменяет релиз).
- Уже было и сохранено: публикация в PyPI по OIDC без токенов с аттестациями сборки (проверено: у v0.36.1 есть provenance), CodeQL, Dependabot (pip, Docker, Actions), ключ подписи в Action во временном файле с правами 600.

## Проверено, проблем не найдено

- История git (226 коммитов): ключей, токенов, приватных ключей нет.
- `.npy` не распаковывается через pickle (`allow_pickle=False`, тест).
- MCP HTTP-режим слушает только `127.0.0.1` с защитой от DNS-rebinding (значения по умолчанию SDK 2.x).
- Вставка текста на странице проверки — только через `textContent` (XSS невозможен).
- HTML-отчёт экранирует все поля (фаззинг с вредоносными строками).
- Подделка подписи: изменение любого поля сертификата делает подпись недействительной (600 мутаций: подпись действительна ровно тогда, когда байты канонического JSON совпадают).

## Не сделано или принятый риск (нужны решения)

| Что | Почему | Предложение |
|---|---|---|
| Semgrep в CI | Реестр правил недоступен из среды разработки, проверить конфигурацию нельзя | Добавить отдельным PR, когда можно будет проверить; CodeQL и Bandit уже покрывают Python |
| Бинарник `mcp-publisher` качается из `releases/latest` без проверки контрольной суммы | Из среды нет доступа к релизам этого репозитория, чтобы взять хеш | Закрепить версию и SHA-256 в `publish.yml` (владелец, из браузера) |
| `--isolate` — не граница безопасности | Нативный код (ctypes, расширения C) обходит хуки аудита Python | Уже задокументировано; для чужого кода — контейнер `docker/verify/Dockerfile` |
| Минимальная версия MCP SDK (`mcp>=1.10`) | Защита от DNS-rebinding появилась в SDK позже | Поднять минимальную версию после проверки совместимости |
| Content-Security-Policy для страницы проверки | GitHub Pages не позволяет задавать заголовки | Мета-тег через переопределение шаблона MkDocs (отдельный PR) |
| Ротация ключей подписи | Нет описанного процесса | Описать в SECURITY.md/руководстве: новый ключ, старый остаётся для проверки прошлых сертификатов |

## Что должен сделать владелец в настройках GitHub

1. Settings → Code security: включить **Private vulnerability reporting** (ссылка в SECURITY.md ведёт на него), **Dependabot security updates**, **Secret scanning** и **Push protection**.
2. Settings → Branches: защита ветки `main` (обязательные проверки CI, запрет force-push).
3. После первого запуска `scorecard.yml` — добавить бейдж Scorecard в README (результат появится на securityscorecards.dev).
