## 2. Цель и принципы

Цель этапов 8–10: сделать Monte-Neo инструментом, которому доверяют настолько, что без него не принимают ни одну стратегию (человека или ИИ), и добавить то, чего нет ни у кого: проверенный поиск индикаторов, который честно считает собственные попытки.

Принципы «швейцарских часов»:
1. **Истина по построению.** У каждой гипотезы известный ответ, потому что мы сами построили её дефект (а не потому что мы так считаем). Второй, независимый оракул (возмущение будущего в эталонной реализации, не использующий код верификатора) подтверждает метку.
2. **Измеряем, а не утверждаем.** Для каждого класса: полнота (recall) и доля ложных обвинений с доверительными интервалами Уилсона; публикуем «известные пробелы».
3. **Честный отрицательный результат** — функция продукта (в том числе у генератора).
4. **Воспроизводимо и детерминированно**: те же входы → тот же id сертификата, на любом Python и с numba и без.
5. **Не расширять охват ценой ложных обвинений**: новая проверка принимается, только если проходит честный корпус.

Ключевые метрики приёмки (подробно в разделе 8): полнота утечек ≥ 98 % (по каждому классу ≥ 95 %), доля ложных обвинений ≤ 1 % (верхняя граница 95 % ДИ ≤ 3 %), `zoo-lite` ≤ 3 минуты, мутационная оценка ядра ≥ 80 %.

## 3. Этап 8 — «Зоопарк гипотез»: 1000+ проверок, оформленных как наука

### 3.1 Что считаем гипотезой

Гипотеза = (механизм дефекта или условие, форма записи/окружение, ожидаемый вердикт-оракул). «Проверка ловит `shift(-1)`» и «проверка ловит `shift(-1)`, спрятанный в лямбде» — разные гипотезы, потому что ломаются разные части кода. Реестр: `tests/zoo/registry/` (по одному файлу на класс, поля: `id`, `class`, `statement`, `construction`, `oracle`, `expected`, `severity`, `status`). Статусы: `planned` → `confirmed` (верификатор ведёт себя как ожидалось) / `gap` (не ловим, записано в «известные пробелы») / `bug` (исправляем) / `wrong-expectation` (ошибочный оракул).

Портфель/вселенная (60):** выживаемость; веса по будущей капитализации; поперечные ранги по будущему; вселенная, выбранная «сегодня»; ребалансировка по будущему; нормировка по всей вселенной; нехватка символа в части периода; одинаковые символы с разными регистрами; несколько символов на одну метку.

**A11. ML (80):** утечка метки; масштабирование/PCA/кластеризация на всех данных; shuffle-CV; CV без purge/embargo; подбор гиперпараметров на тесте; ранняя остановка по тесту; отбор признаков на всех данных; target encoding по всей выборке; перекрытие меток; повторное использование hold-out; случайное зерно как параметр; обучение на будущем в «онлайн»-цикле; предсказание, записанное в таблицу и считанное обратно; нейросеть, запомнившая последовательность (размер модели ≥ данных).

**A12. Котировки (50):** расширение набора аудита задержки: порядок прихода, ложные «опережения», разные лаги по биржам, замороженные котировки, пересечённые стаканы, часы биржи/часы получателя.

### 3.4 Как устроено

- **Фабрики, а не ручные файлы.** `tests/zoo/factory/` генерирует стратегию из (механизм, форма записи, набор данных) по шаблону; метка (`leaks=True/False`) задана таблицей механизмов и перепроверена независимым оракулом: оракул запускает эталонную реализацию на двух таблицах, совпадающих до момента `t` и различающихся после `t`, и сравнивает позиции в `t` (не использует код верификатора).
- **Уровни запуска:** `zoo-lite` (≈ 150 случаев, по одному на класс и форму) на каждом PR, ≤ 3 мин; `zoo-full` (≈ 2 400) ночью и перед релизом, параллельно (xdist), ≤ 30 мин; `fuzz` (10 000 конфигураций) еженедельно. Релиз блокируется, если `zoo-full` красный или оценка хуже предыдущей.
- **Ошибки как данные.** Каждое расхождение — запись в реестре: исправить продукт, исправить оракул или записать «известный пробел» с обоснованием.
- **Публичная таблица:** `docs/guides/honesty-scorecard.md`, собирается автоматически при релизе: «ловит X из N вариантов утечки (95 % ДИ …), ложно обвиняет Y из M честных (95 % ДИ …), известные пробелы: …». Это главный аргумент доверия и материал для публикаций.
- **Мутационное тестирование ядра** (`mutmut` на `verify/lookahead.py`, `stats.py`, `engine.py`, `weight_engine.py`): оценка ≥ 80 %, неубитые мутанты разбираются.
- **«Дикий» корпус (необязательно, с согласия владельца):** сотни открытых стратегий с GitHub, обезличенно, только агрегаты (без названий проектов): сколько реальных стратегий проходят, сколько отвергаются и почему. Это даёт настоящую оценку, а не синтетическую. Юридически и этически: без публикации имён, ссылок, кода.

## 4. Этап 8.B — защита от обмана и состояния (сначала, это P0)

Причина: находка F1. Реальные случаи: глобальная модель, обученная при импорте на всём CSV; `lru_cache`; предвычисленный массив; «тетрадь» с общим состоянием между ячейками. Стратегия не обязательно злонамеренна, достаточно небрежной. Меры (каждая измеряется классом A3):

1. **Свежий процесс на каждый зонд** (`--isolate` или по умолчанию для зондов): состояние между вызовами не сохраняется. Закрывает кэш между вызовами, не закрывает обучение при импорте на полной таблице.
2. **Зонд чувствительности к данным («кросс-набор»):** вызвать `signal` на посторонней таблице с тем же индексом (случайное блуждание, другой seed): если позиции совпадают с позициями на настоящих данных больше, чем допускает случайность, стратегия не читает данные, а помнит ответ. Закрывает готовый массив и обучение при импорте.
3. **Зонд сдвига времени и масштаба:** те же цены с другим масштабом (×k) и сдвинутым индексом: сигнал, зависящий только от формы цены, не должен измениться; сигнал, привязанный к меткам времени, должен.
4. **Линтер состояния:** `.fit(` на уровне модуля; чтение данных при импорте; `functools.lru_cache`/глобальные словари, изменяемые из `signal`; присваивание `global`; запись результатов в файл. Предупреждение, не отказ (ложные обвинения дороги).
5. **Проверка правдоподобия результата (`implausible_performance`):** Sharpe, кривая капитала без просадок (Ulcer-индекс), доля прибыльных баров, отношение прибыли к издержкам — сравнить с эмпирическим распределением честных стратегий нашего корпуса для данной частоты; предупреждение (не отказ) при выходе за 99,9-й перцентиль; в сертификате пояснение «слишком хорошо: проверьте утечку через состояние».
6. **Детерминизм-зонд:** два запуска в разных процессах дают один результат; расхождение — зависимость от времени/случайности/окружения.
7. **Честная формулировка в документации:** верификатор запускает код стратегии и не может доказать отсутствие утечки; он поднимает планку доказательств. Угрозы описаны в `SECURITY.md`.

Приёмка: ≥ 95 % случаев A3 получают предупреждение или отказ; доля ложных обвинений на A2 не растёт (контролируется `zoo-full`). Релиз: v0.51.0 («защита от обмана»), P0, делается до расширения зоопарка, потому что зоопарк должен показать, что защита работает.

## 4.1 Этап 8.C — индикатор не перерисовывается (repaint): ни в истории, ни на текущем баре

Требование владельца (04.10.2026): индикатор не должен менять сигналы ни на уже закрытых барах, ни на текущем (формирующемся) баре. Перерисовка — это расхождение между тем, что видно на истории, и тем, что видел бы трейдер в реальном времени: на графике красивые развороты, а вживую сигнал появлялся и пропадал. Это отдельный класс обмана, родственный look-ahead, но не тождественный ему.

**Два вида перерисовки и как их ловить:**

1. **Перерисовка истории (retro-repaint).** Значение индикатора и сигнал на баре `t` меняются после прихода баров `t+1…`. Примеры: ZigZag, фракталы Билла Вильямса без задержки подтверждения, pivot-точки по «будущим» барам, `rolling(center=True)`, Ichimoku chikou, любое «подтверждение» задним числом. Что уже есть: зонд усечения сравнивает позиции на префиксе и на полной таблице, но это 12 контрольных точек и сравнение позиций, а не значений индикатора. Что добавить:
   - режим **«каждый бар»**: для строгой проверки (`--repaint strict`) значения и сигнал пересчитываются на префиксах для всех `t` в окне (или на плотной сетке с гарантированными точками вблизи конца таблицы), допуск 0 для сигнала и 1e-9 относительный для значений;
   - отчёт `repaint_history`: доля баров, у которых сигнал изменился, максимальная глубина изменения (на сколько баров назад «переписано»), первый такой бар;
   - **двусторонний зонд**: кроме усечения справа, добавление баров справа (продлить ряд синтетикой с теми же свойствами): сигнал на прежних барах не должен измениться.
2. **Перерисовка на текущем баре (live-repaint).** *Уточнение при реализации (05.10.2026): сигнал по закрытию бара по определению зависит от цены закрытия, поэтому «мерцание» у любого такого правила не является ошибкой. Проверка различает два свойства: «известен на открытии бара» (не читает собственные цены бара: проходит) и «решается по закрытию» (info: действовать только после закрытия). Проваливается только стратегия, которая заявила `--signal-timing open`, но зависит от цен формирующегося бара. Показатель `flicker_rate` в сертификате победителя `discover` не равен нулю по определению; вместо него пишется `confirmation: close` и статус `repaint_history`.* Сигнал на формирующемся баре зависит от промежуточных `high/low/close` и исчезает или меняется к закрытию. Типичные источники: расчёт на `close` незакрытого бара, `high/low` бара в условии входа, мультитаймфрейм без сдвига (`resample('D').last()` с протяжкой, `request.security(..., lookahead_on)`), Heikin-Ashi и Renko, пересчёт индикатора на каждом тике. Зонд **«снимки внутри бара»**:
   - для контрольных баров `t` собрать таблицу, где бар `t` заменён состоянием в момент 25 %, 50 %, 75 % своего пути (детерминированный синтетический путь `open → low/high → close` с сохранением инвариантов `low ≤ open, close ≤ high`; при наличии тиков или котировок — реальный путь из них, этап «время прихода данных»);
   - сравнить сигнал, полученный на снимке, с сигналом на закрытом баре: если стратегия заявляет решение «по закрытию» (режим по умолчанию), то сигнал по снимку не должен *появляться и исчезать* (мерцание): считаем `flicker_rate` — долю баров, где сигнал на снимке отличается от итогового;
   - для режима «внутрибарного исполнения» (если стратегия явно его заявляет) проверяется обратное: решение принимается на снимке и не должно отменяться к закрытию (иначе позиция открыта по сигналу, которого к закрытию «не было»).
3. **Согласованность режима с исполнением.** Сигнал, посчитанный на баре `t` по его закрытию, исполняется не раньше `t+1` (это уже обеспечивает движок, `fill_at`); добавить проверку, что адаптер или стратегия не исполняет его на `t` по цене закрытия без заявления режима (иначе на живом счёте он недостижим).
4. **Ревизии данных.** Бар `t` может быть пересчитан поставщиком после закрытия (особенно объём): зонд «ревизия» слегка возмущает последние `k` баров и проверяет, что сигнал на уже закрытых барах старше `k` не меняется.

**Статусы в сертификате.** `repaint_history` — провал (REJECT) при любой перерисовке истории, т.к. бэктест тогда показывает то, чего не было; `repaint_live` — предупреждение при `flicker_rate` выше порога (порог калибруем на корпусе), провал, если сигнал заявлен «по закрытию» и при этом прибыль держится на барах с мерцанием (т.е. результат зависит от того, что недостижимо вживую). Чтобы не ломать `--recheck` и идентификатор сертификата, строки ложатся в `info`, пока их вердикт не включён в `reproducibility` отдельным решением владельца (как сделано для ledger).

**Связь с остальными этапами:**
- *Зоопарк:* новый класс **A14 «перерисовка»** (≈ 60 механизмов × 6 масок): ZigZag, фракталы (с задержкой подтверждения и без), pivot, swing high/low, SuperTrend с пересчётом, Heikin-Ashi/Renko, HTF-ресемплинг (с `shift(1)` и без), `lookahead_on`, chikou, `center=True`, «подтверждённый» сигнал со сдвигом `n` (честный двойник), индикатор на закрытии (честный двойник). Для каждого оракул: позиции на барах `≤ t` не меняются при добавлении баров, и сигнал по снимку внутри бара совпадает с итоговым только у честных.
- *`suggest_fix`:* предлагать задержку подтверждения (`shift(n)` для фракталов), `shift(1)` для HTF и замену `.iloc[-1]` незакрытого бара.
- *`discover`:* канарейки получают перерисовывающие формулы (ZigZag-подобное, центрированное окно, HTF без сдвига); **шлюз причинности дополняется зондом снимков внутри бара**: кандидат, мерцающий на формирующемся баре, исключается из поиска. В сертификат победителя пишется `flicker_rate = 0` как проверенное свойство.
- *Линтер:* правила `repaint_zigzag`, `htf_without_shift`, `lookahead_on`, `unconfirmed_pivot` (предупреждения).
- *Ledger:* перерисовка не меняет учёт попыток.

**Приёмка 8.C:** полнота A14 ≥ 98 % для перерисовки истории и ≥ 95 % для мерцания на текущем баре; ложные обвинения на честных двойниках ≤ 1 %; накладные расходы строгого режима ≤ 2× от обычной проверки на 50 000 барах (обычный режим: плотная сетка у конца таблицы, не все бары); 0 мерцающих кандидатов среди победителей `discover` на калибровочных прогонах.

Версия: вместе с зоопарком (часть 2, v0.53) как P1: зонд ретро-перерисовки входит в 8.B-зонды по умолчанию на плотной сетке, строгий режим и снимки внутри бара — флаги `--repaint`.

## 5. Этап 9 — «Проверенный генератор индикаторов» (`monte-neo discover`)

### 5.1 Что есть сегодня

Модуль `core/generator*.py` + `indicators/code_gen.py`/`dynamic.py`: случайные выражения над `data[...]`, эволюция, Монте-Карло-проверка (перемешивание, шум) на Apple-стеке (MLX/Metal). Недостатки с точки зрения доверия: (а) отбор лучшего из тысяч кандидатов на тех же данных (сильное подглядывание в данные), без дефляции Sharpe и без учёта числа испытаний; (б) выражения интерпретируются как строки Python (ограниченный `exec`), а не как грамматика с доказуемыми свойствами; (в) нет гарантии каузальности каждого кандидата; (г) нет итогового сертификата и воспроизводимого журнала поиска; (д) зависимость от тяжёлого стека (на этапе плана он заморожен как исследовательский).

### 5.2 Идея: единственный генератор, который знает, сколько раз он смотрел

Продукт: **честный поиск**. Пользователь (или агент) даёт цены и бюджет; получает либо «найден индикатор, вот доказательства», либо «ничего значимого на этих данных нет». Второе — тоже результат. Уникальность: ни один известный генератор признаков/стратегий не пересчитывает собственные попытки в статистику и не проверяет значимость самого поиска.

Сквозные свойства:

1. **Грамматика, каузальная по построению.** Типизированный DSL (дерево операций, не строки Python): у каждой операции заданы `lookback`, каузальность и тип; запрещены отрицательные сдвиги, центрированные окна, полновыборочные статистики. Библиотека ≈ 80 операций (скользящие средние/EMA/std/min/max/ранг/z-score нарастающим итогом, RSI, ATR, стохастик, разности, отношения, лаги, пересечения, пороги, объём, поперечные операции для вселенной). Каждый кандидат: (а) каузален по типам; (б) дополнительно проходит быстрый динамический зонд усечения (сравнить `f(x[:t])[t]` и `f(x)[t]` в нескольких случайных точках); (в) сериализуется в читаемый `strategy.py` без `eval` чужих строк.
2. **Счётчик попыток и эффективное число независимых испытаний.** Все оценённые кандидаты логируются (хеш канонической формы, дубликаты склеиваются); похожие по выходу кластеризуются (кластеризация корреляций доходностей), получаем `N_eff`, которое идёт в DSR и PBO вместо ручного `n_trials`.
3. **Три барьера значимости:** (а) Reality Check/SPA по всем кандидатам (уже есть в `verify/reality.py`); (б) PBO (CSCV) по матрице кандидаты × периоды; (в) **замок на последней части данных (lockbox)**: последние 20 % истории не видны поиску, открываются один раз, в сертификате флаг «lockbox opened: once».
4. **Нулевой тест самого поиска («search-null»):** тот же поиск (тот же бюджет и семена) прогоняется на K суррогатах (блочный бутстреп/фазовая рандомизация цен с сохранением волатильности); распределение лучшего балла под нулевой гипотезой даёт эмпирическое p-значение процедуры: «ваш лучший Sharpe 1,9; на суррогатах 95-й перцентиль 2,3: значимости нет». Это строгий аналог Reality Check без допущений о форме распределения.
5. **Тест-канарейки:** в поиск подмешиваются заведомо утекающие выражения (отдельная служебная грамматика, не доступная пользователю); если хоть одна канарейка получила высокий балл или вошла в финалисты, поиск аварийно останавливается с объяснением: ловушка в самом конвейере.
6. **Затратный балл:** издержки и оборот в функции приспособленности с самого начала (иначе поиск находит «стратегии оборота»).
7. **Результат:** `strategy.py` (читаемое выражение, параметры, окна), сертификат `strategy-verdict/1` через обычный `verify_strategy` (с `N_eff`, ссылкой на журнал поиска, флагом lockbox, результатом search-null), отчёт «Что искали, сколько, что осталось, сравнение с нулём», журнал поиска (jsonl) для `--recheck`.
8. **Агентный сценарий:** MCP-инструмент `discover_indicator` и команда `monte-neo discover --ohlcv data.csv --budget 20000 --null-runs 50 --lockbox 0.2`. Агент получает честный ответ вместо «лучшего из 300 попыток».

### 5.3 Движок

Новый лёгкий пакет `monte_neo.discover` на numpy/numba (без MLX/Metal): векторизованная оценка пакета кандидатов на сетке окон, позиции = функция сигнала, доход через уже проверенный целевой движок весов с издержками. Ориентир производительности: ≥ 5 000 кандидатов/сек на 10 000 баров (проверить измерением до обещаний). Старый `core/generator*` не удаляется без вашего решения; помечается как «наследие» с указателем на `discover`.

### 5.4 Калибровка (доказательства, что генератор честный)

- **Шум:** на 200 наборах чистого случайного блуждания доля поисков, объявивших «найдено», ≤ 5 % (цель α) с ДИ.
- **Мощность:** на синтетике с известным краем (AR(1)-моментум, возврат к среднему, сезонность) кривая обнаружения по силе края и длине выборки; публикуем «минимально обнаруживаемый край» для 1 000/3 000/10 000 баров.
- **Канарейки:** 100 % отвергнуты.
- **Сравнение со старым наивным поиском:** на шуме он находит «Sharpe 2–3» почти всегда, `discover` — почти никогда. Это демонстрация для README и публикаций («Почему лучший из 10 000 индикаторов на шуме выглядит прекрасно»).
- **Воспроизводимость:** тот же вход и seed → тот же id сертификата и тот же журнал.
- **Реальные данные:** дневные ETF и крипто-часы (источники: владелец; сеть среды ограничена); ожидаемо чаще «ничего не найдено»; это принимаем как честный результат.

## 6. Этап 10 — как сделать продукт незаменимым

Принцип: продукт нужен не «когда вспомнили проверить», а встроен в процесс так, что без него ломается. Идеи по убыванию отдачи:

1. **Реестр попыток (Trial Ledger), флагман.** Файл `.monte-neo/ledger.jsonl` в проекте: каждый запуск `verify` записывает нормализованный хеш стратегии, параметры, результат. `n_trials` в сертификате считается **автоматически** по числу различных вариантов за время проекта. ИИ-агент, перебравший 300 вариантов за три дня, больше не может «забыть» их при дефляции Sharpe. Сертификат: «испытаний по реестру: 312». Это решает самый частый скрытый обман (подбор) в корне.
2. **Исправлять, а не только обвинять (`suggest_fix`).** Для ≈ 30 самых частых утечек безопасные переписывания по шаблону (`shift(-1)` → каузальный вариант, центр окна → хвост, статистика по всей выборке → `expanding`, `fit` на всём → только на обучающей части), выдача диффа, цикл агента «verify → fix → verify» в одном MCP-вызове. Для агентов это превращает инструмент из «судьи» в «напарника».
3. **Оракул hold-out для агентов (Thresholdout).** Верификатор хранит секретный отложенный участок и отвечает агенту только «в пределах допуска от обучающего результата / нет» с добавлением шума (механизм Thresholdout, Dwork и др.: ограничивает переобучение при адаптивных запросах); число запросов ограничено и записывается в реестр. Это единственный разумный ответ на «агент подгонял под тестовую выборку по 200 раз».
4. **История сертификатов и дифф между коммитами:** `monte-neo history`: график вердиктов по коммитам; в PR-комментарии таблица «что изменилось: id, Sharpe, чеки, вердикт». Регрессия вердикта блокирует слияние. Делает проверку частью жизни репозитория.
5. **Предварительная регистрация (`monte-neo register`):** хеш гипотезы и параметров до теста; сертификат показывает «предварительно зарегистрировано» и защищает от HARKing.
6. **Портфель и «уровень фирмы»:** проверка набора стратегий вместе: корреляции, эффективное число независимых стратегий, множественное тестирование на весь список («из 40 стратегий в этом квартале одна может блистать случайно»).
7. **Доктор данных (`monte-neo doctor`):** профили частых провайдеров (Binance, Yahoo, Polygon, Databento, TradingView-экспорт, MT5) с известными проблемами (метка начала/конца бара, поправки на сплиты, часовые пояса, нули объёма) и автоматическим предупреждением.
8. **Агентный слой «из коробки»:** готовые правила для Claude Code/Codex/Gemini/Cursor («после каждой стратегии вызови `verify_strategy`; на REJECT вызови `suggest_fix`; не сообщай доходности без сертификата»), шаблоны репозитория, `init-ci` (есть), бейдж и страница проверки подписи (есть).
9. **Публичная витрина:** страница `honesty-scorecard`, лидерборд Honesty Bench, «ловушка недели», отчёты по дикому корпусу. Это распространение и доверие.
10. **Что НЕ делаем:** облачный сервис, исполняющий чужой код без песочницы и правовой проработки; ещё один движок бэктестов.

Позиционирование «дополняем, а не конкурируем»: фреймворки считают результат, мы доказываем, что ему можно верить; делаем то, что им невыгодно или тяжело (проверка кода на утечки независимо от движка, пересчёт чужих сделок вторым движком, подписанный воспроизводимый сертификат, счёт попыток, честный поиск). Адаптеры уже покрывают шесть фреймворков, задача A8 доведёт до одиннадцати с реальными запусками.

## 8. Метрики качества и приёмка (по этапам)

- **Полнота утечек** (A1): ≥ 98 % всего, ≥ 95 % по каждой группе механизмов; пробелы перечислены в scorecard.
- **Ложные обвинения** (A2): ≤ 1 %; верхняя граница 95 % ДИ Уилсона ≤ 3 %.
- **Защита от обмана** (A3): ≥ 95 % предупреждений/отказов; рост ложных обвинений = 0.
- **Перерисовка** (A14): ≥ 98 % для истории, ≥ 95 % для мерцания на текущем баре; ложные обвинения ≤ 1 %; победители `discover` без мерцания.
- **Данные/экономика/статистика/claim:** ≥ 95 % ожидаемых статусов; каждое расхождение закрыто (баг, оракул или пробел).
- **Адаптеры:** 0 расхождений с позицией самого фреймворка по барам на всех 11 × 14 сценариях.
- **Метаморфика/fuzz:** 0 нарушений; детерминизм 100 % (id сертификата не зависит от numba/числа процессов/платформы).
- **Мутационная оценка ядра:** ≥ 80 %.
- **Скорость:** `zoo-lite` ≤ 3 мин; `zoo-full` ≤ 30 мин; `verify` на 100 000 баров ≤ 10 с (измерить и закрепить в тесте).
- **`discover`:** α ≤ 5 % на шуме; кривая мощности опубликована; канарейки 100 % отвергнуты; воспроизводимость 100 %.
- **Ledger:** `n_trials` в сертификате равен числу различных вариантов в журнале (тест); подмена журнала видна (хеш-цепочка).
- **Использование (метрики роста, не качества):** загрузки PyPI/мес., звёзды, число репозиториев с `monte-neo.yml` (поиск по GitHub), число подключённых агентных интеграций, число участников зоопарка (PR с ловушками).

## 11. Приложение: воспроизведение измерений раздела 1

```python
import numpy as np, pandas as pd
from monte_neo.backtest import synthetic_ohlcv
from monte_neo.verify import verify_strategy

df = synthetic_ohlcv(3000, seed=1)

def future(d, k=40):                      # утечка: смотрит на 40 баров вперёд, сглажена, чтобы оборот был малым
    pos = np.sign(d["close"].shift(-k) - d["close"]).fillna(0)
    return pos.rolling(10, min_periods=1).mean().round().to_numpy()

cache = {}
def cached(d):                            # F1: считаем один раз на полной таблице, потом отдаём срезы
    n = len(d)
    if "full" not in cache or n > len(cache["full"]):
        cache["full"] = future(d)
    return cache["full"][:n]

table = future(df)
def memorised(d):                         # F1: готовый массив
    return table[: len(d)]

for name, fn in (("утечка", future), ("кэш между вызовами", cached), ("готовый массив", memorised)):
    r = verify_strategy(df, signal_fn=fn)
    print(name, r["verdict"], f"{r['metrics']['total_return']:+.1%}", f"Sharpe {r['metrics']['sharpe_annualized']:.0f}")
```

Результат на v0.50.0: утечка — REJECT; кэш между вызовами и готовый массив — **PASS** с Sharpe 57. Маскировки одной утечки (12 форм) пойманы все; честные стратегии (8) не обвинены ни в одной утечке.
